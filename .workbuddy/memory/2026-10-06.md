  - `fs.rmSync` 被 WorkBuddy 的**安全刪除**鉤子接管、改走資源回收桶，失敗：

## 教訓

- 搬整個專案時，**先拆 junction 再刪來源**是硬規則。`rm -rf` 對 junction 的行為不可靠
  （Git Bash 可能把它當目錄遞迴進去），會把目標端的檔案一起帶走
- 跨槽「搬移」其實是「複製 + 刪除」，不存在原子的 rename；所以**一定要先驗證再刪**，
  而且複製腳本要寫成**可重跑**（目標檔存在且大小相同就略過），半途失敗才有救
- WorkBuddy 的 `fs.rmSync` 在**桌面等個人目錄**會被導向資源回收桶；
  資源回收桶吃不下／被佔用時會失敗，而且 `cmd rd` 這條後路也會被擋 —— 這種情況下
  **正確做法是回報並請使用者處理，不要一直換招硬刪**

## 怎麼把 WorkBuddy 的工作目錄換到 `E:\AI`

換掉之後舊目錄不再是工作區，`C:\Users\user\Desktop\AI` 才刪得掉。三種方式（由快到慢）：

1. **輸入框指令**：打 `/folder E:\AI` 直接切；打 `/folder` 或 `/cwd` 可查目前在哪
2. **界面**：新建任務視窗左下（或右側）的「選擇工作空間」/「選擇文件夾」→ 瀏覽到 `E:\AI`
3. **檔案總管**：對 `E:\AI` 按右鍵 →「使用 WorkBuddy 打開」（需已安裝右鍵選單）

另外 **系統設置 → 默認工作空間存儲路徑** 建議一起改成 `E:\`，
免得之後新建的工作空間又預設落在 C:（C: 只有 60GB）。

### ⚠ 實測：`/folder E:\AI` 這個指令在本機版本**不生效**
- 使用者實際打了一次，結果那串字**被當成一般訊息送進對話**（沒有被 app 攔截成指令），
  工作目錄仍然是 `C:\Users\user\Desktop\AI`
- 驗證方法：`echo $PWD` → bash 工具的 cwd 每次都由 harness 設成**當前工作區根目錄**，
  所以這個值就是工作區設定的真相（不是上一個指令留下的）
- 可靠的做法只有**界面**：新建任務視窗左下的「選擇工作空間」/「選擇文件夾」→ 選 `E:\AI`
  （或用「打開本地文件夾」）

### 順帶確認的兩件事
- WorkBuddy 的工作區是以路徑 slug 記錄在 `~/.workbuddy/projects/` 下
  （目前是 `c-Users-user-Desktop-AI`；開 `E:\AI` 之後會多一個 `e-AI`）
- **任務歷史／檔案回滾紀錄都存在 `~/.workbuddy/projects/`，不在工作區資料夾裡**，
  所以刪掉 `C:\Users\user\Desktop\AI` **不會**弄丟對話歷史

  而且這個 session 裡**看不到 E: 槽**（`cd /e/AI` → No such file or directory）。
  專案在 C: 這份是完整的 git 工作區（HEAD `27cb682`），所以照舊在 C: 上做
- 使用者要求：「upload to github, main and page (web can run)」，目標 repo 由使用者指定
- 該機器**沒有任何 GitHub 憑證**：沒有 `gh` CLI、`~/.ssh` 是空的、`~/.gitconfig` 不存在、
  repo 沒 remote、`GIT_TERMINAL_PROMPT=0`（所以互動式輸入密碼一定失敗）。
  使用者選了「提供 PAT」，但要**先把 token 要到手才能推**
- 為了讓同一個 repo 既能當專案站台又能跑，做了這些改動（commit `556376d`）：
  - `vite.config.ts` 新增 `resolveBase()`：`GITHUB_ACTIONS` 且有 `GITHUB_REPOSITORY` 時，
    repo 名稱以 `.github.io` 結尾 → `/`，否則 `/<repo>/`；本機一律 `/`；
    可用 `VITE_BASE` 覆寫。**不需要在 workflow 裡設定 base**
  - `navigateFallbackDenylist` 由 `/^\/tessdata\//` 改成 `/\/tessdata\//`（去掉開頭錨定）：
    vitest…不對，是 **Workbox 比對的是含 base 的 `url.pathname`**，部署在 `/<repo>/` 下時
    路徑是 `/Document_inlocal/tessdata/...`，錨定 `^\/` 會失效 → 語言包被當成導覽請求
  - `index.html` 把自己寫的 `<link rel="manifest">` **拿掉**：
    原本寫死 `/manifest.webmanifest`，而 Vite **只會改寫「public/ 裡真的存在」的絕對路徑**
    （`/favicon.svg`、`/icons/*.png` 會被換成 `${base}...`，已實測），
    manifest 是外掛在 build 階段才產生的、不在 public/，所以留在原地 → 子路徑 404。
    好消息：**vite-plugin-pwa 會自己注入** manifest 的 link，且用 `options.base`／`buildBase`，
    dev 與 build 都正確（實測 base=`/Document_inlocal/` 時注入的就是
    `/Document_inlocal/manifest.webmanifest`，且只有一個）
  - `scripts/clean.mjs`：CI 是 Linux runner，原本只叫 `cmd.exe rmdir`，**非 win32 改走 `rmSync`**
  - 新增 `.github/workflows/deploy.yml`（`npm ci` → `npm run build` →
    `upload-pages-artifact` → `deploy-pages`；`configure-pages@v5` 帶 `enablement: true`
    首次會自動把 Pages 來源設成 GitHub Actions）、`public/.nojekyll`、`README.md`
- 因為用 **hash routing**，重新整理任何頁面都不會 404，**不需要 404.html**
- `public/tessdata`（5.2MB）與 `public/tesseract-core`（14MB）在 `.gitignore` 裡 →
  進版控的是來源，CI 靠 `npm run build` 的 `prepare:assets` 自己下載，**所以 runner 需要外網**
- ⚠ **Git Bash 會把「看起來像 POSIX 絕對路徑」的東西改寫成 Windows 路徑**，
  連**命令列參數**與**環境變數值**都會：
  - `VITE_BASE=/mop-ledger/ npm run build` → base 變成
    `C:\Users\User\.workbuddy\binaries\PortableGit\versions\1.2.0\mop-ledger\`，
    `dist/index.html` 全部指到不存在的路徑（**驗證結果會是假的**）
  - `node .smoke/verify-base.mjs /Document_inlocal/` 也一樣：那串**參數**被換成 Windows 路徑
  - 正解：**別把 base 放在命令列或外層環境變數**，寫成腳本裡的預設值、由 Node 自己設定
    `env: { ...process.env, VITE_BASE: base }` 再 spawn（`.smoke/verify-base.mjs` 就是這樣，
    呼叫時**不要帶參數**）。`MSYS_NO_PATHCONV=1` 在這個版本不保證有效

  所以**不能用 curl 判斷 vite preview 有沒有起來**，要看背景任務的 stdout
