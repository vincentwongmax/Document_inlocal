## 教訓

- 搬整個專案時，**先拆 junction 再刪來源**是硬規則。`rm -rf` 對 junction 的行為不可靠
  （Git Bash 可能把它當目錄遞迴進去），會把目標端的檔案一起帶走
- 跨槽「搬移」其實是「複製 + 刪除」，不存在原子的 rename；所以**一定要先驗證再刪**，
  而且複製腳本要寫成**可重跑**（目標檔存在且大小相同就略過），半途失敗才有救
- WorkBuddy 的 `fs.rmSync` 在**桌面等個人目錄**會被導向資源回收桶；
  資源回收桶吃不下／被佔用時會失敗，而且 `cmd rd` 這條後路也會被擋 —— 這種情況下
  **正確做法是回報並請使用者處理，不要一直換招硬刪**

## 怎麼把 WorkBuddy 的工作目錄換到 `E:\AI`

換掉之後舊目錄不再是工作區，`C:\Users\user\Desktop\AI` 才刪得掉。三種方式（由快到慢）：

1. **輸入框指令**：打 `/folder E:\AI` 直接切；打 `/folder` 或 `/cwd` 可查目前在哪
2. **界面**：新建任務視窗左下（或右側）的「選擇工作空間」/「選擇文件夾」→ 瀏覽到 `E:\AI`
3. **檔案總管**：對 `E:\AI` 按右鍵 →「使用 WorkBuddy 打開」（需已安裝右鍵選單）

另外 **系統設置 → 默認工作空間存儲路徑** 建議一起改成 `E:\`，
免得之後新建的工作空間又預設落在 C:（C: 只有 60GB）。

### ⚠ 實測：`/folder E:\AI` 這個指令在本機版本**不生效**
- 使用者實際打了一次，結果那串字**被當成一般訊息送進對話**（沒有被 app 攔截成指令），
  工作目錄仍然是 `C:\Users\user\Desktop\AI`
- 驗證方法：`echo $PWD` → bash 工具的 cwd 每次都由 harness 設成**當前工作區根目錄**，
  所以這個值就是工作區設定的真相（不是上一個指令留下的）
- 可靠的做法只有**界面**：新建任務視窗左下的「選擇工作空間」/「選擇文件夾」→ 選 `E:\AI`
  （或用「打開本地文件夾」）

- WorkBuddy 的工作區是以路徑 slug 記錄在 `~/.workbuddy/projects/` 下
  （目前是 `c-Users-user-Desktop-AI`；開 `E:\AI` 之後會多一個 `e-AI`）
- **任務歷史／檔案回滾紀錄都存在 `~/.workbuddy/projects/`，不在工作區資料夾裡**，
  所以刪掉 `C:\Users\user\Desktop\AI` **不會**弄丟對話歷史

## 白畫面事故：用 Pages 的 base 蓋掉了 `dist/`

- 使用者回報「為什麼現在是白畫面」——**是我造成的**：為了驗證子路徑，
  我用 `VITE_BASE=/Document_inlocal/` 建置，**最後一次建置把 `dist/` 留在 Pages 的 base**。
  `npm run preview` 服務的是 `dist/`，於是瀏覽器去找 `/Document_inlocal/assets/index-*.js`
  → 404 → 白畫面（不是程式壞了）
- 診斷只看一行就夠：`grep -oE 'src="[^"]*index-[^"]*\.js"' dist/index.html`
  → 出現 `/Document_inlocal/...` 就代表 `dist/` 是 Pages 版，`npm run build` 重建即可還原
- 結構性修法：新增 `scripts/deploy-gh-pages.mjs` + `npm run deploy`，
  **建置到 `.deploy/`（已加 .gitignore）再推 gh-pages，永遠不動 `dist/`**
- 該腳本踩到兩個坑（都已修）：
  - `run()` 用 `shell: true` 串指令，**參數含空白會被拆成多個**
    （`-m "deploy: 2026-..."` → `git commit` 把時間當 pathspec 而失敗）→ 訊息改 `deploy-<ISO>`
  - 印指令時會**把 PAT 整串印到終端** → 改成 `token.replace(token, '***')`
- 用 `git push -f <token>@github.com/...` 這種一次性 URL 推送，**不會把 token 寫進
  `.git/config`**（也確認過沒有 credential helper 會存起來），但指令字串本身會留在 log 裡

## GitHub 這邊的狀況（2026-10-06 晚上）

- **GitHub Actions = `degraded_performance`**（官方狀態頁）：第一個 run 排隊 10 分鐘才被
  runner 接走，然後 build 步驟失敗；改成推 `gh-pages` 後 runner 就正常了
- **Pages 的 legacy 建置卡住**：切換來源後 GitHub **沒有自動排建置**（`builds` 是空的），
  手動 `POST /repos/{owner}/{repo}/pages/builds` 才排進去，但狀態一直停在
  `building` 且 `duration: 0`、`updated_at` 不動 → 站台持續 404（"Site not found"）
- 診斷用指令（都靠 PAT）：
  - `GET /repos/{o}/{r}/pages` → 看 `build_type`/`source`/`status`
  - `GET /repos/{o}/{r}/pages/builds/latest` → 看建置有沒有在動
  - `POST /repos/{o}/{r}/pages/builds` → 手動排一次建置（回 `queued` 就代表設定沒問題）
  - `PUT /repos/{o}/{r}/pages` 帶 `{"source":{"branch":"gh-pages","path":"/"},"build_type":"legacy"}`
    切回分支部署；`POST` 帶 `{"build_type":"workflow"}` 則對應 Actions 部署
- 結論：`main` + `gh-pages` 兩邊的內容都正確且已驗證，**卡的是 GitHub 的 Pages 建置服務**
